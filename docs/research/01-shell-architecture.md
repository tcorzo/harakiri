# 01 — Shell + mpv video-surface architecture

Worker slice: how a TypeScript UI coexists with an mpv video surface that must own the HDR swapchain.
Date of research: 2026-10-29. Read-only research; nothing installed.

Evidence key: every version/date/maintenance claim carries `[cmd: …]` or `[url: …]`, or is marked **unverified**.
`gh api repos/X` means `gh api repos/X --jq '{stargazers_count,pushed_at,archived,license}'`.

---

## TL;DR recommendation

1. **Shell: Electron**, with the main process in TypeScript. Native work goes in a small Rust (napi-rs) addon or a Rust sidecar process when needed. Wails v3 is dropped (reasons in §3).
2. **MVP video architecture: "mode switch" (option a).** The library/browse UI runs in an Electron window. Playback spawns the **stock `mpv` binary** as its own process, which owns its own fullscreen toplevel (`vo=gpu-next`, `gpu-api=vulkan`, `target-colorspace-hint=yes`). The app controls it over JSON IPC (`--input-ipc-server`). The player OSD is drawn **inside mpv** by our own mpv JS/Lua script, which gets state from TS through `script-message`, or by TS pushing ASS through `osd-overlay`. With this setup HDR is _by construction_ identical to stock mpv, which is also what the validation harness tests against.
3. **Gamepad is read natively in the Electron main process** (SDL3 via `@kmamal/sdl`, or evdev/libmanette). Input is routed to whichever surface is active (web UI over Electron IPC, mpv over JSON IPC). This avoids the Chromium focus rule and the mpv-window-has-focus problem altogether.
4. **Phase 2 (only if a seamless React overlay over live video is required): the Jellium pattern.** On Wayland, a Rust host uses `wl-proxy` to splice mpv's `xdg_toplevel` surface in as a _subsurface_ of an app-owned toplevel, with the web UI as a sibling subsurface above it. On Windows the equivalent is the mpv HWND plus a DirectComposition visual. On macOS it is the mpv NSWindow plus CAMetalLayer subviews. Treat this as R&D, not MVP.
5. **Do not fork Jellium.** It is GPL-2.0, about 70k lines of Rust plus CEF, and wired to jellyfin-web. Its gamepad issues are open. Study its compositor and proxy code as the reference design.

## 1. How Jellium actually does it (source-read)

Repo: `andrewrabert/jellium-desktop`, tarball at commit `1b73a13` (default branch HEAD, 2026-10-29) `[cmd: gh api repos/andrewrabert/jellium-desktop/tarball]`.
Maintenance: last default-branch commit 2026-10-19 ("Update deps") `[cmd: gh api repos/andrewrabert/jellium-desktop/commits?per_page=5]`. No GitHub releases; builds come as nightly.link CI artifacts `[cmd: gh api repos/andrewrabert/jellium-desktop/releases → empty; README]`. License GPL-2.0 `[file: LICENSE]`. About 70k LOC of Rust `[cmd: find … -name '*.rs' | xargs cat | wc -l → 70128]`.

### Core principle (AGENTS.md)

> "mpv owns its own window + GPU; libmpv is used only for the control plane (properties/commands/events)." CEF "renders the UI as an overlay texture above the video layer."

So Jellium **never** uses the libmpv render API. mpv runs in-process via libmpv, but its VO creates and presents its own native surface with its own swapchain, exactly as the standalone mpv binary does. The app then rearranges _window-system objects_ so that the mpv surface sits under the web overlay. libmpv here is a fork with only 3 commits on top of upstream: `--input-vo-cursor`, `--input-keyboard`, and a w32 icon `[cmd: gh api repos/andrewrabert/mpv/compare/mpv-player:mpv:master...andrewrabert:mpv:jellium-desktop → ahead_by 3, behind_by 637]`. There are no rendering changes, so HDR comes from stock mpv `gpu-next`. mpv 0.41.0 made `gpu-next` the default and added color-management-v1 v2 on Wayland `[cmd: gh api repos/mpv-player/mpv/releases/tags/v0.41.0]`. wp-color-management-v1 support itself landed in 0.40.0 `[same, v0.40.0]`.

### Linux / Wayland: a protocol proxy that turns mpv's toplevel into a subsurface

Files: `src/wayland/src/mpv_host.rs`, `src/wayland/src/mpv_proxy/{mod,app,mpv}.rs`.

- Before `mpv_create`, Jellium starts an **in-process Wayland proxy** built on the `wl-proxy` crate (`wl-proxy = 0.1.4, features=["all-protocols"]`; latest 0.1.5, 2026-10-11, by mahkoh, the author of the Jay compositor) `[file: src/wayland/Cargo.toml; cmd: curl crates.io/api/v1/crates/wl-proxy]`. It then sets `WAYLAND_DISPLAY` to the proxy socket, so mpv's VO connects to the proxy and not to KWin.
- The proxy has two server sides: **S_mpv**, for mpv's connection, and **S_app**, which the app's own Wayland code joins through a `socketpair`. Both are multiplexed onto **one upstream connection** to the real compositor. That is what makes it legal to parent mpv's `wl_surface` under the app's surface: Wayland subsurfaces need parent and child on the same client connection.
- When mpv creates its `xdg_toplevel`, the proxy **intercepts the xdg role** and answers mpv's configure requests itself. It sends MAXIMIZED so mpv keeps the host's size, and it answers but ignores mpv's unmaximize/resize requests ("the host owns geometry"). It then calls `wl_subcompositor.get_subsurface(mpv_surface, host_root)` ("splice") and does `place_above(host_root)`, which puts mpv at the bottom of the root's child stack. It gives mpv an empty input region, so all input goes to the app.
- The mpv subsurface stays in **synchronized mode** forever. Each mpv commit asks for a root commit, so every video frame applies atomically with window geometry (`ChildPresentH`).
- **The CEF web overlay is a sibling subsurface above mpv.** CEF runs windowless (OSR). `OnAcceleratedPaint` shared textures (dmabuf) are imported through `jfn-gpu-paint` (wgpu/Vulkan) or attached straight to a `wl_surface` as a dmabuf, with `wl_shm` as the fallback. The overlay gets transparent pixels where the video should show `[files: src/gpu_paint/src/lib.rs, src/wayland/src/layer.rs, src/jfn_cef/src/web_overlay.rs]`.
- **How HDR metadata reaches the compositor:** the proxy forwards every protocol (`all-protocols`), including `wp_color_management_v1`. mpv/libplacebo therefore sets a PQ/BT.2020 image description _on its own (now sub-)surface_, and KWin composites that surface in its own colorspace next to the sRGB overlay surface. Jellium itself does not touch color management. A grep of `src/**/*.rs` finds only clippy lint entries for color-management methods and no calls `[cmd: grep -rn color_management src]`.
- The toplevel, decorations, fullscreen, and scale all belong to the app (`root_window.rs`, 1418 lines).

### Linux / X11: the same idea with an X11 protocol proxy plus `--wid`

`src/x11/src/mpv_proxy.rs`: mpv's `DISPLAY` points at a proxy that forwards bytes and **SCM_RIGHTS fds**, which DRI3/Present dmabufs need. mpv embeds into an app "video host" window through `--wid`. The proxy neutralizes mpv's `ConfigureWindow`, `SetInputFocus`, cursor, and `_NET_WM_STATE`, so the app is the only window authority. (X11 has no per-surface HDR anyway.)

### Windows: mpv owns the HWND, and CEF is composited on top with DirectComposition

`src/windows/src/render/mod.rs`: "Every frame CEF produces is presented 1:1 under a composition visual. **The composition target is the mpv HWND**". mpv's d3d11 swapchain is the window content, and the CEF OSR frame is a DComp visual above it. There is no `--wid` on Windows. mpv creates the window, and Jellium adopts it.

### macOS: mpv owns the NSWindow, and CEF goes into CAMetalLayer subviews

`src/macos/src/init.rs` waits for mpv's NSWindow, swizzles `windowShouldClose:`, and adds an input view. `compositor.rs` adds one `CAMetalLayer`-backed NSView per CEF surface with `addSubview:positioned:NSWindowOrderingMode::Above`. The CEF frame arrives as an IOSurface through `OnAcceleratedPaint`.

### What is reusable as a pattern

- **Invariant: the VO always presents its own swapchain to the window system.** No GPU-texture handoff into a UI toolkit.
- **The UI is a separate, alpha-blended, compositor-level layer above the video**: a subsurface (Wayland), a DComp visual (Win), or a CALayer (mac). The OS compositor does the HDR+SDR mix with each surface's colorspace intact.
- **On Wayland, a protocol proxy is the only way to make an unmodified mpv VO render into a surface you parent**, because mpv has no Wayland `--wid` (§2c).
- **mpv is authoritative for playback state; the UI only reflects property observations** (AGENTS.md "mpv Event Flow").
- Gotchas they hit: never call sync mpv API from event callbacks (deadlock), and the synchronized-subsurface commit ordering.

### Jellium caveats relevant to us

- Gamepad: open issues #698 "Game controller input does not work", #646 "controller only works on TV mode", #181 "directional button goes to last or first item" `[cmd: gh api search/issues?q=repo:andrewrabert/jellium-desktop+gamepad+OR+controller]`. Gamepad depends on jellyfin-web's own Gamepad API handling inside CEF OSR, so it is not a solved problem there.
- Dolby Vision: issue #245 (open) "DV Profile 7 file outputs HDR10 instead of DV on LG G4 via HDMI". The maintainer says "Probably an upstream mpv issue". A user reports mpv recreates the swapchain and signals HDR10, and `target-colorspace-hint=no` only leaves the TV latched in whatever mode it was already in `[cmd: gh api repos/andrewrabert/jellium-desktop/issues/245/comments]`. **Flag for the HDR worker: "DV out of the box" over HDMI from a PC is not something mpv provides. The realistic target is DV (P5/P7/P8) → PQ HDR10 output through libplacebo.**

## 2. Options for our TS app

Wayland first. "HDR outcome" means: is mpv `gpu-next` free to present a 10-bit swapchain with a PQ/HLG image description to KWin?

### (a) Separate mpv process with its own fullscreen toplevel, controlled by JSON IPC — **RECOMMENDED for MVP**

- **HDR:** full. It is literally stock mpv (`vo=gpu-next`, Vulkan, `wp_color_management_v1`), the same binary and config the harness validates. This holds on Wayland, X11, Windows, and macOS alike.
- **UI during playback:** must be mpv-drawn. Choices: (1) our own mpv JS script (mpv ships a JS/MuJS scripting backend) that renders an OSD with `mp.create_osd_overlay` and receives state and commands from TS through `script-message`; (2) TS sends `osd-overlay` commands with ASS events over IPC. Overlays are scoped to the IPC client and are deleted when it disconnects `[url: https://raw.githubusercontent.com/mpv-player/mpv/master/DOCS/man/input.rst §osd-overlay]`; (3) adopt uosc (LGPL-2.1, 3476★, 5.13.0 on 2026-08-03) `[cmd: gh api repos/tomasklaen/uosc; gh api repos/tomasklaen/uosc/releases/latest]`. Option (1) or (2) keeps the design language under our control. The player UI gets _simpler_ (seek bar, track pickers, skip-intro, up-next), and the rich UI stays in React.
- **Window handoff:** on Wayland a client cannot position or stack toplevels, so handoff is "Electron hides or minimizes, mpv goes fullscreen; mpv exits or idles, Electron shows". Expect a visible flash or mode switch on transitions. KWin can smooth this with window rules. Keeping mpv alive with `--idle=yes --force-window=no` between items avoids respawn cost.
- **Gamepad/focus:** while mpv is fullscreen it holds keyboard focus, so Chromium-side gamepad or keyboard handling in the Electron page is unreliable. Read the gamepad natively in the main process and route it. mpv also has `--input-gamepad` (SDL2, off by default) `[url: options.rst L4712]`, but one router owned by the app is better than two input stacks.
- **Complexity:** low. Node `net` socket plus JSON. No native code is needed for MVP.
- **Platforms:** all.

### (b) Transparent web window stacked over a separate mpv window

- **Wayland: not viable.** There is no client-side global positioning or z-order between two toplevels, so you cannot keep a transparent overlay window glued above mpv's window (KWin scripting could, but that is compositor-specific and fragile).
- Windows/X11: works, and is the pattern used by tauri-plugin-mpv. Its README says "Linux ⚠️ Window embedding is not working" `[cmd: gh api repos/nini22P/tauri-plugin-mpv/readme]`. Stremio shell-ng also uses it (Windows-only, WebView2 over an mpv-rendered window) `[cmd: gh api repos/Stremio/stremio-shell-ng/readme]`.
- HDR on Windows: OK (mpv's d3d11 swapchain). Gamepad: same focus issue as (a).

### (c) `--wid` embedding

- mpv docs list `--wid` semantics for **X11, win32, Android only**. On X11 and win32, mpv creates its own child window parented to the wid `[url: https://raw.githubusercontent.com/mpv-player/mpv/master/DOCS/man/options.rst §--wid]`. **There is no Wayland support.** That is why Jellium needs the proxy, and why Soia and tauri-plugin-mpv fall back on Linux.
- On X11 you still cannot put a transparent web layer _over_ a child window without a compositor-aware ARGB sibling. X11 has no HDR. Windows: a child HWND under a WebView works (ventic does this: "On Linux and Windows the Rust side parents an actual mpv window into the page" `[cmd: gh api repos/ventic/ventic/readme]`. On Linux this is presumably X11/XWayland, **unverified**).

### (d) libmpv render API into the web view / toolkit

- `render.h` offers only `MPV_RENDER_API_TYPE_OPENGL`, `_D3D11`, and `_SW` `[url: https://raw.githubusercontent.com/mpv-player/mpv/master/include/mpv/render.h L52-54]`. There is no Vulkan and no swapchain ownership, so mpv cannot set swapchain colorspace metadata (`--target-colorspace-hint` needs gpu-next with a Wayland/D3D11/winvk swapchain, already established). The host toolkit's surface is SDR 8-bit sRGB. **HDR passthrough dies**, which is exactly jellyfin-desktop issue #523. For Electron there is also no supported path to feed a GL FBO into Chromium short of the experimental `sharedTexture.importSharedTexture` → `VideoFrame` path, which is still SDR. **Dropped.**
- Prior art: Soia (Tauri, 204★) uses a render-context mode on Wayland and states "Dolby Vision is not currently supported on Linux" `[cmd: grep src-tauri/src/mpv/handle.rs in FengZeng/soia tarball; gh api repos/FengZeng/soia/readme]`. Kagami/mpv.js (render-API-in-Chromium via the dead PPAPI) was last pushed 2024-01-17 `[cmd: gh api repos/Kagami/mpv.js]`.

### (e) Electron offscreen rendering (OSR) plus a native compositor

- Electron OSR with `webPreferences.offscreen.useSharedTexture: true` hands the main process an `OffscreenSharedTexture`. On Linux, `handle.nativePixmap` = `{planes[{fd,stride,offset,size}], modifier}`, which is a **dmabuf**. Formats are rgba/bgra/rgbaf16. The texture must be `release()`d quickly, and the handle "cannot be directly passed to another process" `[url: https://raw.githubusercontent.com/electron/electron/main/docs/api/structures/offscreen-shared-texture.md; …/shared-texture-handle.md; …/tutorial/offscreen-rendering.md]`.
- This is exactly Jellium's CEF input format. Combined with a Rust host (napi-rs addon _in the main process_, so fds are valid) that owns its own Wayland connection, toplevel, and mpv proxy, it **reproduces Jellium with Electron in place of CEF**. HDR: full (mpv subsurface). Overlay: full React over live video.
- Costs: you are writing a mini compositor (dmabuf import into `zwp_linux_dmabuf_v1` `wl_buffer`s, synchronized commits, scale, input). All input has to be forwarded into Electron with `webContents.sendInputEvent`. Gamepad API focus inside an OSR page is **unverified**, and native gamepad routing makes it moot. A separate implementation is needed per OS (DComp on Win, CALayer on mac).
- **Variant worth a spike (unverified, novel):** route _Electron's own_ Wayland connection through a wl-proxy (set `WAYLAND_DISPLAY` for Electron), merge it with mpv's connection the way Jellium merges S_app and S_mpv, and splice mpv's surface as a subsurface `place_below` Electron's transparent toplevel surface. Electron keeps its normal on-screen GPU compositing and input with no OSR. The proxy must forward everything Chromium uses (linux-dmabuf, explicit sync, fractional scale, its own subsurfaces). wl-proxy's `all-protocols` suggests that is feasible. Wayland-only.

### (f) Adopt or fork Jellium, or build on CEF directly

- Fork: HDR is proven on Linux/macOS/Windows (user reports, plus mpv-native architecture). But it is GPL-2.0, Rust-only, about 70k LOC, CEF-specific, and shaped around jellyfin-web injection (`src/web/*.js` shims). The UI would still be jellyfin-web unless we replace it, and its gamepad story is open-issue territory. The user's stack (React 19 + Vite + TanStack in TS) would have to live inside CEF with a Rust host, and the TS main-process benefit is lost. **Use as the reference implementation, not as a base.** If the project is GPL-compatible, lifting `mpv_proxy/` (Wayland) and `windows/src/render` is legally possible.
- CEF directly (cef-rs, or C++): the same as the Jellium path without the head start. Dropped.

| Problem                          | Choice                                                                                                                                                                                                                                | Why                                                                                                                                          | Considered & dropped                                                                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Open risks

1. **Mode-switch UX on KWin Wayland:** the transition between the Electron window and the mpv fullscreen toplevel (flash, focus-stealing prevention, HDR mode toggling on the output when mpv appears) is **unverified**. It needs a spike on the actual Plasma box.
2. **The player UI has to be built in ASS/mpv-JS**, not React. Design parity with the library UI costs real effort. If the product demands a React overlay over video, phase 2 becomes a must, and its Wayland proxy work is non-trivial (Jellium's `root_window.rs` alone is 1418 lines).
3. **Dolby Vision over HDMI:** mpv outputs PQ HDR10, not a DV signal (Jellium #245). "DV P5 out of the box" can realistically only mean correct DV→PQ tone mapping by libplacebo. This needs reconciling with the user's stated goal (HDR worker's slice).
4. **Electron OSR on Linux** (phase 2): `nativePixmap` dmabuf import into a separate Wayland connection, and gamepad/focus semantics in OSR pages, are **unverified**. The `sharedTexture` import API is marked Experimental.
5. **WebKitGTK gamepad focus rules and analog buttons** (only relevant if Wails or Tauri is reconsidered): **unverified** beyond bug 328634.
6. **Native gamepad in Electron:** `@kmamal/sdl` last released 2025-08-30, so the binding is about 14 months stale. The fallback is a small napi-rs SDL3/evdev addon.
7. **KDE/KWin specifics** (whether per-surface PQ subsurfaces are scanned out or composited, and whether HDR must be enabled globally in Display settings) belong to the HDR/compositor worker. They affect both phase 1 and phase 2 equally.
