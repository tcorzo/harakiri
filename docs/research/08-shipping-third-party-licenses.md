# 08. Shipping third-party licenses, notices and corresponding source

Researched 2026-11-22. Question: how do established open source apps that redistribute a bundled, GPL-licensed media stack ship license texts, NOTICE files and the GPL corresponding source? We want a convention to copy, not a custom scheme. This is engineering research, not legal advice.

## Summary and recommendation

No single "standard" layout exists for AppImages, but three established conventions combine into one small scheme:

1. **License texts inside the artifact: copy the Flatpak/Flathub layout.** One directory per component, `licenses/<component>/<files>`, which Flathub requires and the freedesktop/GNOME/KDE runtimes populate. Linux distros do the same with `/usr/share/licenses/<pkg>/` (Fedora, `%license`) and `/usr/share/doc/<pkg>/copyright` (Debian). linuxdeploy, the main AppImage tool, copies Debian `copyright` files into `usr/share/doc/<pkg>/copyright`. Electron/electron-builder already puts `LICENSE.electron.txt` and `LICENSES.chromium.html` at the AppImage root.
2. **Source: copy the FFmpeg legal checklist and the GPLv3 §6(d) model.** Host the exact source tarballs, the patches and a build-recipe text file on the same GitHub Release as the AppImage, and put a plain-language pointer next to the download. Linking to upstream alone is permitted by §6(d) ("a different server ... operated by you or a third party") but leaves us responsible for keeping that link alive and for the exact-match requirement, so mirroring is the low-risk reading. For the Fedora RPM-sourced libraries, also attach the matching SRPMs.
3. **Apache-2.0: ship the license text.** shaderc, glslang and SPIRV-Tools contain no NOTICE file in their trees (verified below), so §4(d) is not triggered. §4(a) still requires the license text.

Concrete in-AppImage paths (under the app root next to the Electron binary, which is `$APPDIR` in the AppImage):

- `LICENSE.electron.txt`, `LICENSES.chromium.html` (produced by electron-builder, nothing to do)
- `LICENSE` (harakiri, MIT)
- `resources/mpv/licenses/<component>/...` with one directory per bundled component (`mpv`, `ffmpeg`, `libplacebo`, `sdl2`, `curl`, `shaderc`, `glslang`, `spirv-tools`, `spirv-headers`, `nv-codec-headers`, plus one per RPM-sourced library). RPM-sourced directories are filled from `rpm -qL <pkg>` (the files under `/usr/share/licenses/<pkg>/`).
- `resources/mpv/licenses/README` stating the bundle is GPLv3 as a whole, that mpv runs as a separate process, how to get the source (the release assets below), and the build line.
- `resources/mpv/BUILDING.txt` (FFmpeg checklist item 6: the configure line and how it was built) and `resources/mpv/SOURCES.txt` (name, version, sha256, upstream URL, or the SRPM NEVRA, per component).

Release assets per tag (all on the same GitHub Release, GPLv3 §6(d), FFmpeg checklist items 7 and 8):

- `harakiri-x86_64.AppImage`, `latest-linux.yml` (existing)
- `harakiri-mpv-bundle-sources-vX.Y.Z.tar.xz`: the pinned upstream tarballs (mpv, libplacebo, FFmpeg, SDL2, nv-codec-headers, curl, shaderc, glslang, SPIRV-Tools, SPIRV-Headers) plus the `mpv/` recipe directory (`Containerfile`, `build.sh`, `fetch.sh`, `versions.env`, `host-libs.txt`, patches) at the release tag. Or one asset per tarball if size matters; the recipe archive is the part that must exist.
- `harakiri-mpv-bundle-srpms-vX.Y.Z.tar` (or loose `.src.rpm` files): the Fedora 44 SRPMs for every RPM-copied library, fetched with `dnf download --source <pkg>` at the same NEVRA that was installed.
- `SHA256SUMS` covering the above.

Things I could not verify are listed under "Unverified" at the end.

## 1. Prior art: what real projects ship

### Electron and electron-builder

- Electron's own Linux dist zip ships `LICENSE` and `LICENSES.chromium.html` next to the binary. Electron's docs tree shows this layout (`LICENSE`, `LICENSES.chromium.html` beside the app) in https://github.com/electron/electron/blob/main/docs/tutorial/snapcraft.md and lists both in `script/zip_manifests/dist_zip.linux.x64.manifest` (https://github.com/electron/electron/tree/main/script/zip_manifests).
- electron-builder keeps them by default. `retainElectronLicenseFiles` in https://github.com/electron-userland/electron-builder/blob/master/packages/app-builder-lib/src/electron/ElectronFramework.ts says: "The Electron dist ships Electron's own `LICENSE` and Chromium's `LICENSES.chromium.html` next to the binary, and both licenses require them to be retained in distributables. On win/linux they stay next to the executable." It renames `LICENSE` to `LICENSE.electron.txt`. The changeset https://github.com/electron-userland/electron-builder/blob/master/.changeset/mac-electron-license-files.md confirms the macOS bundle now matches "the license files already shipped on Windows and Linux" (issue 9407). So on Linux there is nothing to configure. We should check the built AppImage contains both (`mise run package:check` could assert it).
- Chromium generates `LICENSES.chromium.html` (about:credits) with `tools/licenses/licenses.py credits`, which reads each third_party directory's `README.chromium` and its "License File" field (https://chromium.googlesource.com/chromium/src/+/109.0.5414.119/tools/licenses.py, older revision; current path is `tools/licenses/licenses.py`, https://sources.debian.org/src/chromium/138.0.7204.157-1/tools/licenses/licenses.py). A remoting example invokes it with the `credits` argument and a template (https://chromium.googlesource.com/chromium/src.git/+/lkgr/remoting/credits/credits.gni). We do not generate it; Electron's release process does.
- Built-in option for extra license files: none that matters. The AppImage target `license` option is an end-user license dialog shown on first launch, not a notices mechanism (https://www.electron.build/docs/appimage). To add files use `extraResources` (copied into the `resources` directory, which is where the mpv bundle already goes) or `extraFiles` (copied to the app root on Linux) (https://www.electron.build/docs/linux search result; the `extraFiles` wording "the same as extraResources but copy into the app's content directory (Contents for MacOS, root directory for Linux and Windows)" is from the electron-builder configuration reference).

### Apps that bundle mpv or FFmpeg

- **jellyfin-desktop** (https://github.com/jellyfin/jellyfin-desktop): ships one aggregated text file, `resources/misc/licenses.txt`, compiled into the binary as a Qt resource (`QFile licenses(":/misc/licenses.txt")` in `src/main.cpp`) and shown in the app. It contains only the BSD-style notices (Broadcom RPI decoder, HIDRemote) in the part I read. It has a `debian/copyright` and `dev/appimage/` (Dockerfile, `build.sh`, `AppRun`) for its AppImage. I did not find a license directory or a source tarball convention in the AppImage build; `build.sh` has no license handling. This is the weakest precedent for us.
- **IINA** (https://github.com/iina/iina): macOS app bundling libmpv and FFmpeg. It keeps the repository `LICENSE` and an in-app acknowledgements file, `iina/Credits.rtf`, which lists libmpv and FFmpeg with their copyright and license text (https://github.com/iina/iina/blob/develop/iina/Credits.rtf). Its libraries come from `other/download_libs.sh`. Source is the public repo plus upstream; it does not host source tarballs next to the binary in the files I looked at.
- **shinchiro/mpv-winbuild-cmake** (https://github.com/shinchiro/mpv-winbuild-cmake): the repo is the build recipe (CMake, `packages/`, `scripts/`, toolchain); it has a target "ninja download" that "Download all packages' sources at once without compiling" (README). It contains no LICENSE aggregation at the top level (tree search found no license-named files). The recipe-is-the-source pattern is what our `mpv/` directory already is.
- **OBS Studio** (https://github.com/obsproject/obs-studio): ships `COPYING`, a `frontend/data/license/gplv2.txt` shown in its About dialog (`frontend/dialogs/OBSAbout.cpp`) and per-dependency license files kept in the dependency directories (`deps/*/LICENSE*`). Its Flatpak (https://github.com/flathub/com.obsproject.Studio) is built from the manifest, so the manifest is the source and recipe (see Flatpak below).
- **VLC, Kdenlive, Shotcut AppImages**: not examined in primary sources. Unverified.

### Flatpak and Flathub

- Flathub requirements (https://docs.flathub.org/docs/for-app-authors/requirements): "License must be correctly declared in the metainfo file". Each module's license files must be installed to `$FLATPAK_DEST/share/licenses/$FLATPAK_ID`, with a subdirectory per module when done manually: `install -Dm0644 LICENSE -t $FLATPAK_DEST/share/licenses/$FLATPAK_ID/<module-name>`. Every dependency must be declared as a source with a public URL; non-redistributable sources use `extra-data`.
- flatpak-builder 1.4.5 and later "automatically recognizes and includes common license files" for the app and bundled libraries, with the manifest key `license-files` to fine-tune. For apps built from DEB or RPM binaries, Flathub tells maintainers to include the license files explicitly "for consistency and auditability". The runtimes include license and copyright notice files themselves under `/usr/share/licenses`. Source: https://docs.flathub.org/blog/enhanced-license-compliance-tools. The module property `license-files` is in https://docs.flatpak.org/en/latest/flatpak-builder-command-reference.html. This is the layout to copy: it is the only mainstream packaging format with a stated rule for per-bundled-library license directories.

### Debian copyright format (DEP-5) and REUSE

- DEP-5 (https://www.debian.org/doc/packaging-manuals/copyright-format/1.0/) standardises the machine-readable `debian/copyright` file (Header stanza with `Format`, then `Files`, `Copyright`, `License` stanzas). Debian Policy 12.5 (https://www.debian.org/doc/debian-policy/ch-docs.html): "Every package must be accompanied by a verbatim copy of its distribution license(s)", installed as `/usr/share/doc/PACKAGE/copyright`, not compressed and not a symlink; common licenses (GPL, Apache-2.0) may point to `/usr/share/common-licenses` instead. So DEP-5 describes a source package's file; the installed `copyright` file is what ships in binaries. For a bundle of upstream libraries it is a plausible format for one aggregate `copyright` file but offers nothing a plain per-component directory does not.
- REUSE (https://reuse.software/spec-3.3/) is about marking each file in a source project: `LICENSES/` at the project root, `SPDX-License-Identifier` headers, optional `REUSE.toml`. The spec "does not explicitly address distributing binaries". It does not apply to shipping licenses with a binary. It would only help to mark harakiri's own source files, and is out of scope here.

### AppImage tooling

- **linuxdeploy** copies copyright files itself. `src/core/appdir.cpp` has `deployCopyrightFiles`, which finds the owning package with `dpkg-query -S` and copies `/usr/share/doc/<pkg>/copyright` to the same path under the AppDir (`src/core/copyright/copyright_dpkgquery.cpp`), and can be switched off (`disableCopyrightFilesDeployment`; the darktable build script sets `DISABLE_COPYRIGHT_FILES_DEPLOYMENT=1`). Sources: https://github.com/linuxdeploy/linuxdeploy/blob/master/src/core/appdir.cpp and https://github.com/linuxdeploy/linuxdeploy/blob/master/src/core/copyright/copyright_dpkgquery.cpp. It works only on dpkg systems; on Fedora there is no equivalent, which is why our RPM-copy step must do it explicitly.
- **appimage-builder** recipes include and exclude `usr/share/doc/*` entries by glob (e.g. https://github.com/AppImageCrafters/appimage-builder/blob/master/recipes/gimp/AppImageBuilder.yml excludes `usr/share/doc/*/README.*`, `changelog.*`), so it treats `usr/share/doc/<pkg>/` as the place; I found no rule keeping `copyright` there deliberately. Weak evidence.
- The AppImage project states its own license does not cover AppImage contents (libappimage `debian/copyright`, https://sources.debian.org/src/libappimage/1.0.4-5-7/debian/copyright). I found no AppImage specification text on license layout (the draft spec covers icons and AppStream only).

## 2. GPL corresponding source for binaries on GitHub Releases

- GPLv3 §1 defines Corresponding Source as "all the source code needed to generate, install, and (for an executable work) run the object code and to modify the work, including scripts to control those activities", excluding System Libraries and unmodified general-purpose tools. It explicitly includes "the source code for shared libraries and dynamically linked subprograms that the work is specifically designed to require". Source: https://www.gnu.org/licenses/gpl-3.0.txt. So the build recipe is part of the obligation, and the private shared libraries in `resources/mpv/lib` are inside the scope.
- GPLv3 §6(d): "Convey the object code by offering access from a designated place (gratis or for a charge), and offer equivalent access to the Corresponding Source in the same way through the same place at no further charge. ... If the place to copy the object code is a network server, the Corresponding Source may be on a different server (operated by you or a third party) that supports equivalent copying facilities, provided you maintain clear directions next to the object code saying where to find the Corresponding Source. Regardless of what server hosts the Corresponding Source, you remain obligated to ensure that it is available for as long as needed to satisfy these requirements." (https://www.gnu.org/licenses/gpl-3.0.txt). §6(a)/(b)/(c) are for physical media and written offers and are not our case.
- GPL FAQ (https://www.gnu.org/licenses/gpl-faq.html): "If you make object code available on a network server, you have to provide the Corresponding Source on a network server as well. The easiest way to do this would be to publish them on the same server, but ... you can alternatively provide instructions for getting the source from another server, or even a version control system. No matter what you do, the source should be just as easy to access as the object code, though ... The sources you provide must correspond exactly to the binaries." On separate sites: "Yes. Section 6(d) allows this. However, you must provide clear instructions people can follow to obtain the source, and you must take care to make sure that the source remains available for as long as you distribute the object code." Also "Corresponding source means the source from which users can rebuild the same binary."
- FFmpeg's legal checklist (https://ffmpeg.org/legal.html): item 3 "Distribute the source code of FFmpeg, no matter if you modified it or not"; item 4 "Make sure the source code corresponds exactly to the library binaries you are distributing"; item 5 `git diff > changes.diff` for your own changes; item 6 "Explain how you compiled FFmpeg, for example the configure line, in a text file" in the source root; item 7 package the source as a tarball or zip; item 8 host the source on the same webserver as the binary. Item 1 notes `--enable-gpl` makes the whole of FFmpeg GPL ("If those parts get used the GPL applies to all of FFmpeg"). Item 2 asks for dynamic linking. This is the closest thing to a published recipe for what we do.
- SFLC Guide to GPL Compliance (https://softwarefreedom.org/resources/2014/SFLC-Guide_to_GPL_Compliance_2d_ed.html): corresponding source includes "the source code, build scripts, makefiles, configuration files and other materials necessary to build" the executable; a redistributor "may not merely pass along" an upstream's written offer if commercial ("it is never sufficient to merely pass along the same written offer"); even redistributors of someone else's software are bound ("even if you merely redistribute software produced by someone else"); "the full license text must accompany every distribution" (GPLv2 §1 discussion); the guide quotes §6's "may be on a different server (operated by you or a third party)". Only the first 100,000 characters of the page were read.
- Linux Foundation, Practical GPL Compliance (https://www.linuxfoundation.org/hubfs/Reports/Practical_GPL_Compliance_Digital.pdf), "Pitfall #6: Missing Build System": publishing sources without "the Makefiles, configurations, and patches" is wrong because patches are missing and "Makefiles and other build scripts often contain configuration options ... Without this information, the binary cannot be rebuilt". Supports shipping the recipe.
- SFC's enforcement strategy page (https://sfconservancy.org/copyleft-compliance/enforcement-strategy.html) names "the scripts used to control compilation and installation of the executable" (GPLv2 wording). I found no SFC or FSF page that says "linking to upstream is enough" or "is not enough" for a redistributor who builds their own binary; the textual answer is §6(d) above.

Answers to the sub-questions:

- Publishing the exact upstream tarballs plus the build recipe as release assets: this is what FFmpeg items 4, 6, 7 and 8 describe and what GPLv3 §6(d) and the FAQ call the easiest route. I did not find a survey proving it is "standard practice" across AppImage projects; jellyfin-desktop and IINA do not appear to do it for the artifacts I read. Treat it as the conservative convention, not a measured norm.
- Upstream URLs alone: allowed in form by §6(d) only if the directions sit next to the binary and the source stays available and exact. Our tarballs are sha256-pinned, so a verifiable pointer is possible, but we then depend on every upstream keeping old tarballs forever. Mirroring removes that dependency. Recommendation: mirror.
- Build scripts: required by the §1 definition and by the FFmpeg and LF guidance. The `mpv/` recipe directory is that.

## 3. Apache-2.0 for shaderc, glslang, SPIRV-Tools (statically linked)

- Apache-2.0 §4 (https://www.apache.org/licenses/LICENSE-2.0.txt): (a) give recipients "a copy of this License"; (b) mark changed files; (c) keep notices in Source form; (d) "If the Work includes a "NOTICE" text file as part of its distribution, then any Derivative Works that You distribute must include a readable copy of the attribution notices contained within such NOTICE file ... in at least one of the following places: within a NOTICE text file distributed as part of the Derivative Works; within the Source form or documentation ...; or, within a display generated by the Derivative Works". The NOTICE contents "do not modify the License".
- Do these repos have NOTICE files? Checked through the GitHub tree API on 2026-11-22: google/shaderc has `LICENSE`, `AUTHORS`, `third_party/LICENSE.glslang`, `third_party/LICENSE.spirv-tools` and no `NOTICE`; KhronosGroup/glslang has `LICENSE.txt` and a `LICENSES` directory and no `NOTICE`; KhronosGroup/SPIRV-Tools has `LICENSE` and no `NOTICE` (only `utils/vscode/src/lsp/LICENSE`); SPIRV-Headers has `LICENSE` and `LICENSES`. https://github.com/google/shaderc, https://github.com/KhronosGroup/glslang, https://github.com/KhronosGroup/SPIRV-Tools, https://github.com/KhronosGroup/SPIRV-Headers. Re-check at the pinned tags, since the tarballs are what ship.
- What must ship: the Apache-2.0 text and each project's own license/copyright file (glslang's `LICENSE.txt` is a collection of BSD, MIT and Apache terms for its parts; ship it whole), in `licenses/shaderc/`, `licenses/glslang/`, `licenses/spirv-tools/`, `licenses/spirv-headers/`. Static linking inside `libplacebo.so` changes nothing: the notices travel with the bundle, not the object file. If a pinned tag does gain a `NOTICE`, copy it into the same directory (§4(d) permits "a NOTICE text file distributed as part of the Derivative Works").
- Other licenses in the bundle (from the repos' top-level files): mpv `Copyright`, `LICENSE.GPL`, `LICENSE.LGPL`; FFmpeg `COPYING.GPLv2`, `COPYING.GPLv3`, `COPYING.LGPLv2.1`, `COPYING.LGPLv3`, `LICENSE.md`, `CREDITS`; libplacebo `LICENSE` (LGPL-2.1); SDL `LICENSE.txt`, `CREDITS.md`; curl `COPYING` and `LICENSES` (https://github.com/mpv-player/mpv, https://github.com/FFmpeg/FFmpeg, https://github.com/haasn/libplacebo, https://github.com/libsdl-org/SDL, https://github.com/curl/curl). Copy these from the pinned tarballs at build time (the recipe's `build.sh`), not by hand.

## 4. Libraries copied out of Fedora 44 RPMs

The coordinator's list: libass, freetype, fontconfig, harfbuzz, graphite2, fribidi, glib2, pcre2, libselinux, libunistring, libidn2, libuchardet, libunibreak, lcms2, libpng, zimg, dav1d, luajit, brotli, bzip2, xz, nghttp2, krb5 family, keyutils, libcom_err.

- License text: collect from the RPM, not by hand. `rpm -qL <pkg>` (short for `--licensefiles`: "only include license files", checked locally with `rpm --help`) lists the package's license files, for example `rpm -qL glib2` printed `/usr/share/licenses/glib2/LGPL-2.1-or-later.txt`. Fedora's Licensing Guidelines treat `rpm -q --licensefiles` as the test that all relevant license files are in a package (https://docs.fedoraproject.org/en-US/packaging-guidelines/LicensingGuidelines/, quoted via a mirror search result; the page itself blocked automated fetches). Caveat from a Fedora list discussion: Fedora does not strictly require `/usr/share/licenses`, only `%license`-tagged files, so use `rpm -qL`, not a path glob. The Debian analogue is `/usr/share/doc/<pkg>/copyright`, which linuxdeploy copies (section 1).
- Flathub's rule for RPM- or DEB-binary apps is the same: include each package's license files explicitly, in a per-module directory (https://docs.flathub.org/blog/enhanced-license-compliance-tools).
- Source for LGPL/GPL RPM libraries: the same GPLv3 §6(d) reasoning applies, with these LGPL differences. LGPLv3 §4 (https://www.gnu.org/licenses/lgpl-3.0.txt) requires "a copy of the GNU GPL and this license document" (4b) and either conveying relinkable source (4d0) or "a suitable shared library mechanism" (4d1), which is dynamic loading of a private copy. LGPLv2.1 has analogous terms (not fetched). Shipping them as `.so` files in `resources/mpv/lib` is the shared-library route; the user can swap the files in an extracted AppImage. glib2, fribidi, libunistring, libidn2, keyutils, graphite2 are the LGPL ones per the coordinator. Also still ship their license text.
- Established practice for obtaining source: mirror the matching SRPM. Fedora's own source tree is `Everything/source/tree/Packages/` on mirrors and the release tree (https://ftp.riken.jp/Linux/fedora/releases/42/Everything/source/tree/Packages/a is an example listing); `dnf download --source <pkg>` is an alias of `--srpm` (checked locally with `dnf download --help`). After end of life Fedora moves the release to `/pub/archive/fedora/linux/releases/<n>` and keeps source trees there (e.g. https://dl.fedoraproject.org/pub/archive/fedora/linux/releases/21/Everything/source/SRPMS/e/ and the EOL runbook, https://docs.fedoraproject.org/en-US/infra/release_guide/sop_release_eol/ via search result; the runbook page itself was blocked). I found no stated retention period.
- Is pointing at Fedora's archive enough? By §6(d) text a third-party server may host the source if we give clear directions next to the binary and "remain obligated to ensure that it is available". It is not a statement that Fedora's archive meets that duty for us, and the version must match exactly the NEVRA we copied (the Fedora updates repo replaces older builds, which is why exact-NEVRA SRPMs matter). Safe practice: attach the SRPMs of the exact installed NEVRAs to the release. I did not find a written FSF/SFC statement endorsing or rejecting "point at the distro's archive" for a redistributor; the SFLC guide's warning against merely passing along an upstream offer points to mirroring.
- How Flatpak/Snap/AppImage bundlers satisfy this: Flathub builds everything from source declared in the manifest, so sources are public by construction, and `flatpak-builder --bundle-sources` can create a source runtime ("Create an additional runtime with the source code for this module", flatpak-builder reference above). For AppImage and Snap bundlers that copy distro binaries I did not find a documented convention; linuxdeploy copies only the copyright file, not source. Flag as unverified: that no AppImage tool automates SRPM or source collection.

## 5. Implications for the recipe (what the build must do)

- `mpv/build.sh` copies, for each source-built component, the license files named above from the pinned tarball into `licenses/<component>/`, and for each RPM-copied library runs `rpm -qL <pkg>` and copies those files into `licenses/<pkg>/`.
- It also writes `SOURCES.txt` from `versions.env` (names, versions, sha256, URLs) and the installed RPM NEVRAs (`rpm -q --qf '%{NAME}-%{VERSION}-%{RELEASE}.%{ARCH}\n'`), and `BUILDING.txt` with the configure and meson lines.
- The release workflow assembles the source tarball (pinned upstream tarballs from `fetch.sh`, the `mpv/` recipe at the tag) and runs `dnf download --source` for the listed packages inside the same Fedora 44 container, then uploads both next to the AppImage with `SHA256SUMS`.
- A check in `mise run package:check` should assert that `LICENSE.electron.txt`, `LICENSES.chromium.html` and every `lib/*.so` have a matching `licenses/<component>/` entry, so a new bundled library without a license directory fails the build (our rule: enforced by a test).

## Unverified or open

- Whether VLC, Kdenlive, Shotcut and jellyfin-desktop AppImages ship source assets or license directories: not examined or not found.
- Chromium's current generator path and the exact contents of Electron 45's `LICENSES.chromium.html` were not inspected; electron-builder's behaviour is taken from its source and changeset, not from opening a built AppImage.
- Fedora Licensing Guidelines and the EOL runbook pages blocked automated fetches; claims about them come from search result excerpts.
- Whether `rpm -qL` captures every license text for each of the listed packages (some Fedora packages tag few files as `%license`) must be checked per package in the container; a package with no license file needs a manual fix.
- No FSF, SFC or other primary statement found on whether pointing at a distro's SRPM archive alone suffices; the recommendation to mirror is our conservative reading of §6(d), not a ruling. This is not legal advice.
