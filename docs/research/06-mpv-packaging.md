# 06 — Controlling mpv from TS, getting the right mpv build, packaging

Research date: 2026-10-29. Read-only. Every version or maintenance claim names the command or URL that backs it. Claims I could not check are marked `unverified`.

## TL;DR

- **Control path:** write our own typed JSON IPC client, about 200 lines on `node:net` plus zod. The protocol is small, stable and documented. No npm library meets the bar: they are either stale or have one maintainer and no TS-first design.
- **The big new finding is Dolby Vision Profile 7 with a full enhancement layer (FEL).** It needs **mpv master plus libplacebo >= 7.387.0**. mpv v0.41.0, Fedora 44 and Flathub cannot merge the FEL. They handle P5, P8 and P7 base layer + RPU only.
- **Fedora 44:** mpv 0.41.0 and libplacebo 7.360.1 are fine for the P5/P8/HDR10+/Wayland-HDR MVP. Fedora's `ffmpeg-free` cannot decode HEVC, so it is unusable for us. RPM Fusion `ffmpeg` 8.1.3, already installed here, has every decoder we need.
- **Shipping:** bundle a pinned mpv binary per platform and spawn it as a child process. Use shinchiro builds on Windows and the official mpv macOS zips or an IINA-style build on macOS. On Linux, ship a Flatpak (freedesktop 26.08 runtime + ffmpeg-full extension) that builds mpv and libplacebo from pinned sources. An AppImage is the secondary target.
- **Packager:** use **electron-builder**, which has AppImage, Flatpak, deb and rpm targets plus `extraResources` for the mpv binary. Use electron-vite only as the dev/bundle layer. Forge is the fallback because it has 5 maintainers and an official flatpak maker.

## 1. Controlling mpv: JSON IPC

Source: https://raw.githubusercontent.com/mpv-player/mpv/master/DOCS/man/ipc.rst (fetched 2026-10-29).

- **Transport:** `--input-ipc-server=<path>` creates a unix socket on Linux/macOS or a named pipe on Windows (`\\.\pipe\name`). The alternative is `--input-ipc-client=fd://N`, where we pass a pre-connected socketpair fd and need no filesystem path. That is a nice fit for spawning from Node with `stdio: [..., 'pipe']`. Windows `fd://` support for `--input-ipc-client` arrived in v0.39.0 (release notes, `gh api repos/mpv-player/mpv/releases/tags/v0.39.0`).
- **Framing:** UTF-8 JSON, one message per `\n`-terminated line.
- **Requests:** `{"command": ["name", ...args], "request_id": <int>}`. Named-arg form: `{"command": {"name": "loadfile", "url": ...}}`. Replies are `{"error":"success","data":...,"request_id":N}`. Replies can interleave with events, so correlate by `request_id` and never assume order.
- **Async:** `"async": true` (example in the doc: `{ "command": ["screenshot"], "request_id": 123, "async": true }`). The reply arrives when the command finishes and the socket does not block meanwhile.
- **Properties:** use `get_property`, `set_property`, and `observe_property <id> <name>`. Changes then arrive as `{"event":"property-change","id":1,"name":"volume","data":52.0}`. Use `unobserve_property <id>` to stop. Our `observe_property` ids are a separate number space from `request_id`.
- **Events:** `start-file`, `file-loaded`, `end-file` (with `reason`, `file_error`), `seek`, `playback-restart`, `shutdown`, `log-message` (after `request_log_messages`), `client-message`.
- **client-message:** a Lua/JS script inside mpv calls `mp.commandv("script-message", ...)`, and the IPC client gets `{"event":"client-message","args":[...]}`. Use it for gamepad/OSD hooks that must live inside mpv (`unverified` detail of the exact field name; check against ipc.rst when implementing).
- **Useful properties for us:** `track-list` (it includes `dolby-vision-profile` and `dolby-vision-level` since v0.39.0, per the release notes), `video-params` (`gamma`, `primaries`, `sig-peak`), `audio-codec-name`, `current-ao`, `audio-device-list`, `hwdec-current`.

### Proposed client shape (~200 LOC)

- `MpvConnection` wraps `net.connect(path)`, uses a line splitter, and keeps a `Map<request_id, {resolve, reject, timer}>` of pending requests.
- `command<T>(args, schema?)` returns `Promise<T>` and validates `data` with zod when a schema is given.
- `observe<K extends keyof Props>(name)` returns an AsyncIterable or emitter, typed through a `Props` map with zod schemas for each property.
- Handle reconnect, timeouts and `shutdown`, and make the mpv process lifecycle (spawn, kill, exit code) part of the same module.
- Test it against a real headless mpv (`--idle --vo=null --ao=null`) in the test runner.

Verdict: hand-rolled wins. Every npm option is stale, a beta, or has a single maintainer with no typed property model (registry search `curl 'https://registry.npmjs.org/-/v1/search?text=mpv%20ipc&size=20'`, `...text=mpv`, `...text=libmpv`; per-package `curl https://registry.npmjs.org/<pkg>`). The protocol has been stable for years, so reversing the decision costs almost nothing.

### What Fedora 44 ships

`dnf info --cacheonly mpv libplacebo ffmpeg-free libavcodec-free`; `rpm -q ...`; `rpm -qi ffmpeg`:

- `mpv-0.41.0-5.fc44` (fedora repo; not installed)
- `libplacebo-7.360.1-3.fc44` (installed). **No FEL.**
- `ffmpeg-free-8.1.3-1.fc44` / `libavcodec-free-8.1.3-1.fc44` (updates; not installed)
- **Installed:** `ffmpeg-8.1.3-1.fc44`, Vendor/Packager: RPM Fusion. `ffmpeg -decoders` shows hevc, av1, libdav1d, vvc, ac3, eac3, dca (DTS), truehd.

Fedora `ffmpeg-free` codec gaps (https://src.fedoraproject.org/rpms/ffmpeg/raw/f44/f/ffmpeg.spec line ~902 `--disable-decoder="h264,hevc,vc1,vvc"`; `enable_decoders` allowlist):

- **No HEVC decode at all**, and VA-API hwaccel cannot help because the native decoder is disabled. This kills 4K HDR and DV. H.264 works only through openh264 (limited). No VC-1, no VVC.
- Allowlist includes `ac3`, `dca`, `mlp`, `truehd`, `aac`, `libdav1d`. `eac3` was **not found** in the f44 allowlist (grep). Missing E-AC-3 decode would break PCM fallback for DD+ (passthrough is fine).
- Conclusion: we require RPM Fusion `ffmpeg-libs` (swap `ffmpeg-free` → `ffmpeg`) or a bundled ffmpeg. That is a strong argument for Flatpak/AppImage with ffmpeg-full.

## 3. Distribution: shipping a known-good mpv

Model: **the app spawns its own mpv binary** with `--input-ipc-server` (or `--input-ipc-client=fd://`). mpv owns its own toplevel window and swapchain (`--vo=gpu-next --gpu-api=vulkan --target-colorspace-hint`). A user-configured system mpv is allowed as an override.

- **Windows:** vendor `mpv.exe` (and optionally `libmpv-2.dll`) from shinchiro `mpv-winbuild-cmake` (latest tag 20261021, `gh api repos/shinchiro/mpv-winbuild-cmake/releases`). Builds static FFmpeg/libplacebo from git master. Alternatives: `zhongfly/mpv-winbuild` (2026-10-29-cf764c61d1) or the official release zip `mpv-v0.41.0-x86_64-pc-windows-msvc.zip` (`gh api repos/mpv-player/mpv/releases/latest --jq '.assets[].name'`). Put it under electron-builder `extraResources` → `process.resourcesPath/mpv/mpv.exe`.
- **macOS:** official `mpv-v0.41.0-macos-{14,15,26}-arm.zip` / `macos-15-intel.zip` exist (same command). Re-sign the nested binary with our identity and notarize it. IINA v1.5.0 (2026-10-03) shows a shipping libmpv bundle (`gh api repos/iina/iina/releases`). stolendata builds: `unverified`. For FEL on macOS we would need a master build: self-built or a CI artifact from `mpv-player/mpv` git-release (`unverified` whether macOS artifacts are attached to git-release).
- **Linux:**
  - **Flatpak (primary):** freedesktop 26.08, ffmpeg-full, modules libplacebo 7.387.0 + mpv master, Electron app as the main binary. Needs `--device=dri`, `--socket=wayland`, `--filesystem=xdg-run/pipewire-0`. Electron needs `--socket=fallback-x11` and zypak or `--no-sandbox` handling (`unverified`: electron-builder flatpak target uses org.electronjs.Electron2.BaseApp).
  - **AppImage (secondary):** bundle a self-built mpv + libs. The host Vulkan/Mesa driver must stay on the host, so don't bundle libvulkan ICDs.
  - **RPM/deb:** depend on the distro `mpv` (degraded: no FEL; on Fedora the user also needs RPM Fusion).

## 4. Electron specifics

- **Wayland native by default since Electron 38.** From breaking-changes.md "Breaking API Changes (38.0)": "Removed: `ELECTRON_OZONE_PLATFORM_HINT`… default value of `--ozone-platform` changed to `auto`… Electron now defaults to running as a native Wayland app when launched in a Wayland session (`XDG_SESSION_TYPE=wayland`). Force XWayland with `--ozone-platform=x11`." (https://raw.githubusercontent.com/electron/electron/main/docs/breaking-changes.md). Electron 45.1.0 is current (2026-10-27).
- Flags: `--enable-features=WaylandWindowDecorations` (CSD) and `--enable-wayland-ime` are commonly used (`unverified` for current necessity). The Gamepad API on Wayland works through Chromium's evdev/udev path (`unverified`).
- **Electron 42 dropped the `postinstall` download.** "`electron` no longer downloads itself via `postinstall` script… downloads itself dynamically the first time its main `bin` script is run" (breaking-changes.md, 42.0). The package now ships the `install-electron` bin (`curl https://registry.npmjs.org/electron/latest | jq .bin`). So **no `trustedDependencies` entry is needed for electron** under bun. It is on bun's default trusted list anyway (https://raw.githubusercontent.com/oven-sh/bun/main/src/install/default-trusted-dependencies.txt, which lists `electron` and `esbuild`). For CI and packaging, run `bunx install-electron` (or let electron-builder fetch its own copy via `@electron/get`) and cache `~/.cache/electron`.
- **Runtime:** the Electron main process runs Electron's bundled Node (Electron 45 → Node 24.x, `unverified` exact). Main-process code must target Node APIs, not `Bun.*`. bun is the package manager, script runner and test runner for pure-TS modules only. The IPC client uses `node:net`, so it runs both under bun (tests) and under Electron (prod).
- **Critical Wayland caveat:** mpv `--wid` embedding is **not supported on Wayland**. mpv must be its own toplevel. Overlaying an Electron UI on top of the mpv window is not controllable on Wayland: there is no stacking or positioning, and Electron cannot use layer-shell. Practical options:
  1. During playback, mpv is fullscreen and the playback UI is drawn by mpv itself (an OSD Lua script such as uosc, or our own script driven by `script-message`/`client-message`). Electron handles browse UI only.
  2. Electron UI rendered into mpv through `overlay-add` (a raw BGRA buffer, high CPU).
  3. libmpv render API inside Electron, which loses swapchain ownership and HDR. **Reject.**

  This is the biggest architectural risk in this slice. Option 1 is what the spawn model implies. On Windows/X11, `--wid` embedding does work.

## Open risks

1. **Wayland: no embedding or overlay.** Playback UI must live inside mpv (OSD script). It also affects the gamepad input path: during playback mpv has focus, so gamepad input must be read either by mpv or by a background reader (evdev/SDL) in the Electron main process, which needs device permissions.
2. **DV P7 FEL requires mpv master + libplacebo 7.387.0.** That means shipping a git snapshot of mpv, which is less stable than a release, and FEL decode is two HEVC streams (GPU/hwdec load). The next mpv release date is unknown.
3. **Fedora codec split.** RPM installs on a stock Fedora have no HEVC. Flatpak avoids this.
4. Single-maintainer npm risk for electron-builder and electron-vite (Forge is the fallback).
5. HDR10+ metadata passthrough to the display and compositor support for color-management-v1 v2 are `unverified` per compositor.
6. TrueHD/DTS-HD MA passthrough through PipeWire depends on the HDMI sink's IEC958 config. This needs a hardware test.
7. macOS/Windows FEL builds: shinchiro builds master, so Windows is likely fine. On macOS we may need our own build.
